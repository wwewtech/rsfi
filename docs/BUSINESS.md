> **Статус документа**: Актуальная инженерная спецификация (август 2026)

## 1. Рыночный контекст: Кому нужен быстрый L1-фильтр

### Проблема

С 2 августа 2026 года вступили в силу ключевые положения **EU AI Act**, требующие от систем высокого риска (финансы, медицина, юридический сектор) обеспечить:
- **Аудируемость** — полная трассировка каждого запроса и ответа
- **Робастность** — устойчивость к adversarial-атакам и prompt injection
- **Прозрачность** — объяснимость решений о блокировке

Рынок AI-безопасности растёт с CAGR >25%, при этом идёт активная консолидация:
- **Lakera** → поглощена **Check Point**
- **Prompt Security** → поглощена **SentinelOne**
- **Robust Intelligence** → поглощена **Cisco** (лежит в основе Cisco AI Defense)
- **Arthur AI** — продолжает работать как платформа для enterprise AI agent security

### Архитектурный тренд: трёхслойная защита

Все зрелые enterprise-решения к 2026 году перешли к стратегии **«Three-Clocks»**:

| Уровень | Задержка | Что делает | Примеры |
|:--------|:---------|:-----------|:--------|
| **L1 — Fast-path фильтр** | < 1 мс | Геометрическая/статистическая проверка эмбеддингов, детерминированные правила | **RSFI**, regex/NLP sanitizers |
| **L2 — Inference sidecar** | 50–150 мс | Специализированные классификаторы (ProtectAI-deberta, NeMo Guardrails) | Meta Llama Guard 4, Guardrails AI |
| **L3 — LLM-as-a-Judge** | > 500 мс | Полноценная LLM-проверка для асинхронного аудита | GPT-4o/Claude для пост-обработки |

**RSFI занимает уровень L1** — самый быстрый слой, который отсекает очевидные атаки до того, как запрос достигнет дорогих L2/L3 систем.

### Кто это покупает

| Сегмент | Боль | Почему L1-фильтр критичен |
|:--------|:-----|:--------------------------|
| **Финтех / банки** | Prompt Injection → несанкционированный вызов Tool Use (перевод средств, доступ к БД) | Каждый запрос к агенту проходит через gateway; L2 на 150 мс × 10 000 rps = невозможно |
| **Здравоохранение** | Галлюцинации в медицинских рекомендациях, утечка PHI/PII | Нужна мгновенная фильтрация до того, как ответ уйдёт пациенту; EU AI Act compliance |
| **Enterprise SaaS** | Agentic AI → агенты выполняют действия (записи в БД, отправка писем); одна инъекция = каскадный отказ | L1-фильтр как «предохранитель» перед инструментами агента |
| **Платформы с мульти-тенантностью** | Разные клиенты, разные SLA, разный уровень риска | Centralized gateway с per-tenant policy enforcement |

## 2. Целевая архитектура: Rust API Gateway + RSFI

### Почему Rust — единственный правильный выбор

Для сервиса, который должен обрабатывать **50 000+ одновременных SSE/gRPC/HTTP2 соединений** с задержкой < 1 мс, выбирать нужно по трём критериям:

1. **Zero GC Pauses** — никаких спайков tail latency из-за сборки мусора
2. **SIMD-векторизация** — скалярные произведения и матричные операции на AVX-512/NEON за микросекунды
3. **Async-сетевой стек** — тысячи конкурентных потоков без GIL и без overhead

| Критерий | Python | Go | **Rust** |
|:---------|:-------|:---|:---------|
| GC Pauses | Есть (CPython) | Есть (1-5 мс) | **Нет** |
| SIMD/AVX-512 | Через numpy (C) | Ограничено | **Нативная автовекторизация LLVM** |
| Async I/O | asyncio (GIL) | goroutines | **Tokio (zero-cost)** |
| Память на инстанс | ~350 МБ | ~100 МБ | **~30-65 МБ** |

**Индустриальные прецеденты**:
- **LiteLLM** — мигрирует горячий путь на Rust (axum), бенчмарки: ~0.05 мс overhead, ~6 800 rps, расход памяти с 359 МБ → 32 МБ
- **AISIX** — open-source AI gateway на Rust, 28 000 rps на 4 vCPU, overhead 0.24 мс p50
- **Cloudflare Pingora** — Rust-фреймворк для прокси, на котором построена вся edge-инфраструктура Cloudflare
- **AgentGateway (Solo.io)** — контроль agentic-трафика (LLM + MCP + Tools)

### Целевой стек

```
┌─────────────────────────────────────┐
│         Клиентское приложение       │
└──────────────┬──────────────────────┘
               │ HTTP/2, gRPC, SSE
               ▼
┌─────────────────────────────────────┐
│    Rust API Gateway (Axum + Tokio)  │
│                                     │
│  ┌───────────┐  ┌────────────────┐  │
│  │ ONNX RT   │  │ RSFI Engine    │  │
│  │ (ort)     │──│ geometry.rs    │  │
│  │ эмбеддинг │  │ whitening.rs   │  │
│  │ < 5 мс    │  │ filter.rs      │  │
│  └───────────┘  │ < 0.02 мс      │  │
│                 └────────┬───────┘  │
│  ┌───────────────────────┘          │
│  │  Decision: PASS / BLOCK / AUDIT  │
│  └───────────┬──────────────────┐   │
│              │                  │   │
│     если PASS            если BLOCK │
└──────┬───────┘          ┌───────┘   │
       ▼                  ▼           │
┌──────────────┐   ┌──────────┐      │
│  LLM Provider│   │  Audit   │      │
│  (OpenAI,    │   │  Log     │      │
│   Llama, etc)│   │  (OTEL)  │      │
└──────────────┘   └──────────┘
```

### Компоненты Rust-сервиса

| Крейт | Назначение |
|:------|:-----------|
| `axum` + `tokio` | Async HTTP/2/gRPC сервер, SSE streaming |
| `ort` (ONNX Runtime bindings) | Локальный инференс эмбеддинг-модели (MiniLM, BGE-M3) без внешних API-вызовов |
| `faer` или `ndarray` | Линейная алгебра: ZCA-матрица, скалярные произведения, QR-разложение |
| `opentelemetry` | Structured tracing для audit trail (EU AI Act compliance) |
| `serde` + `toml` | Конфигурация per-tenant политик (α, β, τ, threat anchors) |

## 3. Известные ограничения и стратегия закрытия

### 3.1. Distribution Drift (уплывание калибровки)

**Суть**: ZCA-матрица вычисляется на калибровочном корпусе. Если домен трафика резко изменится (техподдержка → код на C++ → медицинские тексты), обеливание потеряет точность.

**Закрытие**: Online ZCA Whitening — адаптивная перекалибровка на скользящем окне последних N безопасных запросов. В Rust реализуется как lock-free ring buffer с периодическим пересчётом ковариации.

### 3.2. Evasion через ортогональное подпространство

**Суть**: Принципиально новый паттерн атаки, ортогональный ко всем k threat-якорям, может обойти фильтр (π_thr ≈ 0).

**Закрытие**: MultiDimensionalRSFIFilter с k ≥ 10 разнородными threat anchors (Jailbreak, SQLi, Social Engineering, Data Exfiltration, Code Injection). Для новых категорий — автоматический мониторинг аномально высоких d_M при низком RSFI.

### 3.3. Обфускация (Base64, ROT13, Unicode tricks)

**Суть**: Эксперимент E6 показал: при кодировании атак в Base64/ROT13 ROC-AUC падает до 0.16. Это **фундаментальное ограничение всех геометрических методов** — эмбеддинг-модель не «видит» семантику через обфускацию.

**Закрытие**: Этот класс атак закрывается на L2 (LLM-классификатор) или детерминированным декодером на L1 (regex-based Base64/ROT13 unwrapper перед эмбеддингом).

### 3.4. Зависимость от модели эмбеддингов

**Суть**: Качество RSFI упирается в качество входных векторов. Слабая модель (Word2Vec, базовый BERT) не уловит тонкую грань между «описание взлома» и «запрос на взлом».

**Закрытие**: Использование современных моделей: `all-mpnet-base-v2` (768d), `Qwen3-Embedding` (4096d, ROC-AUC 0.856), `BGE-M3`. При деплое через ONNX Runtime модель работает локально, без внешних API.

## 4. Преимущества RSFI как L1-слоя

| Свойство | Значение |
|:---------|:---------|
| **LLM-agnostic** | Black-Box фильтр. Работает с любой моделью (OpenAI, Claude, Llama, DeepSeek) — ему не нужен доступ к весам |
| **Задержка фильтрации** | ~0.02 мс (без учёта эмбеддинга). Полный пайплайн с локальным ONNX-эмбеддером: 5-10 мс |
| **Математическая гарантия** | Проверяемая пифагорова декомпозиция в касательном пространстве; ортогональность компонент доказана формально |
| **Few-Shot** | 50-200 размеченных примеров для калибровки. Не требует дообучения нейросети |
| **Аудируемость** | Каждое решение раскладывается на d_M, π_thr, v_perp — полная объяснимость для compliance |
| **Честная метрика** | 0.75-0.85 ROC-AUC на hold-out данных (0.856 на Qwen3-Embedding 4096d). Не обещает 1.0 |
